# Zerde 109 — фронтенд: дизайн-документ

**Дата:** 2026-09-09
**Статус:** утверждён (каркас и архитектура согласованы с заказчиком проекта)
**Область:** только фронтенд + лёгкий бэкенд-заглушка на реальных данных. ETL-платформа, дообучение моделей и продовый бэкенд — вне этой спеки.

---

## 1. Цель

Собрать работающий веб-фронтенд системы «Zerde 109» — единый интерфейс трёх модулей
(смарт-приём и маршрутизация, ассистент оператора, ситуационный центр руководителя) —
на реальных исторических данных обращений граждан 109 из 7 регионов Казахстана
(~1 млн строк, ~300 МБ CSV, лежат в `data/`).

Режим работы: инкрементально, рабочий результат каждый день. Жёсткого дедлайна нет,
но каждый шаг оставляет систему в запускаемом состоянии.

## 2. Область работ

### В составе v1
- Монорепо: React SPA (`apps/web`) + Fastify-заглушка (`apps/api`) + общие типы + ингест.
- Слой нормализации: 7 разнородных CSV-схем → единая витрина `appeals` в PostgreSQL 16 (уже установлен локально).
- Все 3 модуля со сквозными фильтрами (регион / период / тема), двумя языками UI (KK / RU), светлой/тёмной темой.
- Предрасчёт аналитики: временные ряды, детектор всплесков (rolling z-score / %), прогноз (сезонный-наив), бэктест-метрики правило-классификатора.
- Экспорт отчётов в PDF / Excel (генерация на сервере).

### Вне области (non-goals, задел на будущее)
- Настоящая KazLLM 8B и дообученная эмбеддинг-модель. В v1 — детерминированный правило-классификатор и интент-паттерны для NL-запросов, **честно помеченные как baseline**, но с реальными метриками на отложенной выборке.
- Настоящая векторная БД (Qdrant/Milvus). В v1 поиск похожих — `pg_trgm` в Postgres.
- Очереди Celery/Redis, авторизация/RBAC, real-time приём из 7 систем-источников.
- Хороплет-карта областей РК (в v1 — рейтинг-бары; карта — стретч).
- Prophet/ARIMA (интерфейс прогноза спроектирован под замену метода).
- Раскатка на 20 регионов, мобильная версия рабочего экрана оператора.

## 3. Архитектура

### 3.1. Стек
- **Фронт:** Vite + React + TypeScript + Tailwind + shadcn/ui, Recharts (графики),
  TanStack Query (данные), React Router (роутинг), react-i18next (KK/RU).
- **Бэк-заглушка:** Fastify + TypeScript, `pg` (node-postgres), `zod` (валидация), `pino` (логи).
- **Хранилище:** PostgreSQL 16, расширение `pg_trgm`.
- **Пакетный менеджер:** npm workspaces (перейти на pnpm, если доступен в окружении).

### 3.2. Структура репо
```
E:\Zerde109\
  apps/web/              Vite + React SPA
  apps/api/              Fastify + TS
  packages/types/        общие TS-типы фронт <-> бэк
                         (Appeal, Kpi, TimePoint, Breakdown, Spike, Forecast,
                          ClassifyResult, ModelEval, NlQueryResult, Meta ...)
  packages/ingest/       CSV (7 схем) -> нормализация -> Postgres; предрасчёт аналитики
  db/migrations/         SQL-схема (нумерованные миграции)
  db/seeds/              справочники: regions, themes, services, theme_map, templates
  data/                  сырые CSV (в .gitignore, не коммитим)
  docs/superpowers/specs/ этот документ
```
Слой доступа к данным на бэке изолирован в модуль-репозиторий, чтобы позже
подменить хранилище/источник без переписывания API.

### 3.3. Поток данных
1. `npm run db:migrate` — накатывает схему.
2. `npm run ingest` (разово / при смене данных) — читает `DATA_DIR`, по каждому региону
   применяет свой маппер, чистит и валидирует строки, батч-апсертит в `appeals`,
   рефрешит матвьюхи, считает `spikes` / `forecasts` / `model_eval.json`.
3. `npm run dev` — параллельно `api` (:3001) и `web` (:5173, прокси `/api` → :3001).
4. Рантайм: web → TanStack Query → `/api/*` → Fastify → `pg` → Postgres.
   UI в v1 не пишет в исходные данные; изменения статусов/черновики оператора идут в
   отдельную таблицу `mutations`.

## 4. Слой данных

### 4.1. Единая витрина `appeals`
7 регионов = 7 разных наборов колонок (проверено по файлам). Маппер каждого региона
приводит строку к одной модели:

| поле | нормализация |
|---|---|
| `id`, `source_id` | синтетический ключ `<код_региона>:<исходный_номер>`, дедуп по нему |
| `region`, `district`, `locality`, `address`, `lat`, `lon` | из имени файла + колонок (где есть координаты — Костанай/Туркестан) |
| `created_at`, `closed_at` | парсинг ~5 форматов дат (`YYYY-MM-DD HH:MM:SS.ffffff`, `DD.MM.YYYY HH:MM:SS`, `M/D/YY H:MM` и т.д.) |
| `theme` | **приведение к таксономии ≥10** по правилам над `category` / `direction` / `servicelevel1` / `category_name` / `sub_category` |
| `raw_category`, `subcategory`, `service_org` | как есть — для трассировки и отладки маппинга |
| `status` | **единый ЖЦ:** `new · routed · in_progress · done · cancelled` |
| `is_overdue`, `sla_days` | из `slabreach` / `deadline` vs `closed_at`/`now` / `expireddays` |
| `channel` | `EKC109 · CallCenter · Mobile · Web · Other` (из `submittal_channel` / `source`) |
| `appeal_type` | `consultation · complaint · incident · info_request` |
| `language` | **эвристика kk/ru** (в данных языка нет): казахские графемы әғқңөұүһі + доля стоп-слов |
| `priority` | **эвристика low/medium/high** (тема + просрочка + тип) — настоящая модель потом |
| `grade`, `operator`, `resolution` | где присутствует в источнике |
| `search_text` | конкатенация текста/категории/адреса для `pg_trgm` |

**Таксономия тем (≥10):** Водоснабжение, Электроснабжение, Отопление, Канализация,
Дороги, Освещение, Благоустройство/Санитария, ТБО/Мусор, Транспорт, Здравоохранение,
Справочная/Консультация, Карантин (legacy COVID), Прочее.

### 4.2. Справочники (seeds)
- `regions(code, name_ru, name_kk, is_active)` — 7 активных + плейсхолдеры к 20.
- `themes(code, name_ru, name_kk, color, sort)` — таксономия + цвет для графиков.
- `services(code, name_ru, name_kk)` — каталог ответственных служб.
- `theme_map(pattern, match_type, theme_code, priority)` — правила ингеста, хранятся для аудита.
- `templates(id, theme_code, service_code, lang, title, body)` — 12–20 типовых ответов RU/KK.

### 4.3. Служебные таблицы и предрасчёт
- `mutations(id, appeal_id, kind, payload_json, created_at)` — правки из UI (смена статуса, черновик).
- Матвьюхи: `mv_daily_counts(region, theme, day, count, overdue_count, avg_close_hours)`,
  `mv_theme_totals`, `mv_region_totals`, `mv_operator_load(operator, region, day, handled)`.
- `spikes(id, computed_at, region, theme, window_days, baseline, current, ratio, zscore, severity)`
  — считает ингест: базовая метрика — z-score дневного счётчика относительно скользящего
  среднего за 28 дней (порог |z| ≥ 2.5); `ratio` (текущее / baseline) показывается рядом
  как человекочитаемый «+300%». `severity` = low/medium/high по величине z.
- `forecasts(id, computed_at, region, theme, month, yhat, yhat_lower, yhat_upper, method)`
  — сезонный-наив на месячном ряде; поле `method` для будущей замены на Prophet.
- `model_eval.json` — бэктест правило-классификатора против исторических меток:
  overall Accuracy + per-category Precision / Recall / F1 / support + матрица ошибок.

### 4.4. Индексы
`appeals`: btree `(region, created_at)`, `(theme, created_at)`, `(status)`;
GIN `pg_trgm` на `search_text`.

## 5. Бэкенд — API (Fastify; относительно исходных данных — read-only)

Общее: маршруты — плагины по модулям; `zod`-схемы на query/body/params через preHandler;
только параметризованный SQL; `@fastify/cors` для дев-режима; конверт ошибки
`{ error: { code, message } }`; пагинация с потолком; таймаут запроса.

### Ситуационный центр
| метод | назначение |
|---|---|
| `GET /api/kpi` | всего за период, Δ к прошлому периоду, доля просроченных, ср. время закрытия, доля повторных, открыто сейчас |
| `GET /api/timeseries` | ряд по `metric`, `granularity=day\|week\|month`, фильтры |
| `GET /api/breakdown` | срез по `dim=region\|theme\|status\|channel` — для баров/донатов |
| `GET /api/spikes` | список выявленных всплесков за период |
| `GET /api/forecast` | история + полоса прогноза по региону/теме на 1–3 мес |
| `POST /api/nl-query` | `{q}` → `{ value\|rows, chart:{type,x,y}, summary, sql }`; интент-паттерн → параметризованный SQL из allowlist; не распознал → 422 с подсказками |
| `POST /api/report` | `{view, filters, format:pdf\|xlsx}` → файл, генерация на сервере (`exceljs` / `pdfkit`) |

### Смарт-приём
| метод | назначение |
|---|---|
| `GET /api/appeals` | пагинация, фильтры (регион/тема/статус/приоритет/поиск), сортировка |
| `GET /api/appeals/:id` | карточка обращения |
| `POST /api/classify` | `{text, language?}` → `{theme, service, priority, language, confidence, entities:{address,object,problem}}`; детект языка + взвешенные правила + приоры; детерминированно, без записи |
| `GET /api/model-eval` | статические метрики из `model_eval.json` |

### Ассистент оператора
| метод | назначение |
|---|---|
| `GET /api/appeals/:id/similar` | K похожих исторических обращений (`pg_trgm` + та же тема/регион) с резолюцией, службой, сроком закрытия, score |
| `GET /api/appeals/:id/duplicates` | почти-дубликаты (открытые) + повторные (тот же адрес, закрыто < 30 дн назад) |
| `GET /api/templates` | шаблоны ответа по теме/службе/языку |
| `POST /api/appeals/:id/route` | смена статуса / сохранение черновика → пишет в `mutations`, исходные данные не трогает |

### Общее
`GET /api/meta` — регионы, темы, службы, каналы, статусы с KK/RU-подписями (фильтры + i18n).

### Заглушки моделей (детали)
- **`/classify`:** детект языка (казахские графемы + доля стоп-слов) → взвешенное совпадение
  по `theme_map` → тема; служба по карте `theme → service`; приоритет по эвристике;
  `confidence` = нормированный отрыв топ-скора; сущности — регулярками
  (адрес: «ул./көше/мкр/дом/№…», объект/проблема — по ключевым спанам). Объяснимо, без LLM.
- **`/nl-query`:** набор интент-шаблонов (regex/keywords → `{metric, dims, filters}`)
  → фиксированный билдер параметризованного SQL (никакой конкатенации пользовательского текста)
  → форма ответа с числом/рядами, авто-графиком и однострочным выводом.
  Стартовый набор интентов v1:
  1. «сколько обращений по <теме> в <регионе> за <период>» → одно число + бар по неделям;
  2. «топ <N> тем в <регионе> за <период>» → горизонтальные бары;
  3. «динамика <темы> в <регионе> за <период>» → линия по дням/неделям;
  4. «доля просроченных по <регионам> за <период>» → бар по регионам;
  5. «сравни <регион A> и <регион B> по <теме>» → две серии.
  Не подошёл ни один → 422 с подсказками. Явно задокументировано как паттерн-матчинг, не NL2SQL-модель.

## 6. Фронтенд

### 6.1. Структура
```
apps/web/src/
  app/                router, провайдеры (QueryClient, Theme, I18n), layout-оболочка
  components/ui/       примитивы shadcn
  components/          общие: ChartCard, KpiCard, DataTable, FilterBar, EmptyState,
                       ErrorBoundary, RankedBarList
  features/
    command-center/    Модуль 3: экраны + хуки + api
    intake/            Модуль 1
    operator/          Модуль 2
  lib/                 api-клиент (fetch + TanStack Query), форматтеры, i18n-словари
  types/               реэкспорт из packages/types
  locales/{kk,ru}.json строки UI
```

### 6.2. Роутинг
- `/` → редирект на `/command-center` (роль Руководитель) или `/operator` (роль Оператор).
- `/command-center` — KPI-строка + вкладки: Обзор · Всплески · Прогноз · Запрос · Отчёты.
- `/intake` — очередь обращений + панель демо-классификации; `/intake/quality` — качество модели.
- `/operator` — список назначенных; `/operator/:id` — трёхколоночный рабочий экран.
- `/appeals/:id` — общая карточка обращения (из очереди и от оператора).
- Состояние глобальных фильтров — в query-параметрах URL (шаримые/закладываемые вью).

### 6.3. Модуль 3 — Ситуационный центр
KPI-строка под FilterBar всегда видна. Ниже — вкладки:
- **Обзор:** линия динамики по дням/неделям/месяцам (переключатель гранулярности,
  вторая серия — просроченные); донат/тримап структуры тем; горизонтальные бары
  топ-10 проблемных категорий (с Δ% к прошлому периоду); рейтинг-лист «обращения по
  регионам» (сортировка по количеству / доле просрочки / ср. времени); бары нагрузки
  на операторов (где есть поле `operator` — ВКО; иначе скрыто с пометкой).
- **Всплески:** строки аномалий (регион + тема + окно + метрика «+300%» + бейдж severity
  + спарклайн); клик → провал в отфильтрованный Обзор. Пустое состояние, когда всплесков нет.
- **Прогноз:** выбор регион + тема → линия истории + полоса прогноза (yhat, lower, upper)
  на 1–3 мес; подпись метода («сезонный-наив»); таблица помесячных чисел.
- **Запрос:** поле ввода + примеры-чипсы («Сколько обращений по дорогам в Шымкенте
  за последний месяц?») → большое число + авто-график + однострочный вывод +
  сворачиваемый показ итогового SQL (прозрачность). Не распознал → «уточни» + подсказки.
- **Отчёты:** выбор вью + фильтры + формат (PDF/Excel) → генерация на сервере, скачивание.

### 6.4. Модуль 1 — Смарт-приём
- **Очередь** (по умолчанию): `DataTable` обращений — №, дата, регион, превью,
  предсказанная тема, служба, приоритет (бейдж), статус, confidence. Серверная
  пагинация + сортировка. Локальные фильтры (приоритет, статус, «низкая уверенность»).
  Клик по строке → `/appeals/:id`.
- **Демо-классификации** (карта/дровер): textarea (KK/RU) → «Классифицировать» →
  карточка результата (язык · тема · служба · приоритет · confidence) + сущности
  (адрес, объект, проблема) + мини-визуализация маршрута (обращение → служба) +
  сворачиваемый строгий JSON. «Загрузить пример» — случайное историческое обращение.
- **Качество модели** (`/intake/quality`): overall Accuracy + таблица по категориям
  (Precision/Recall/F1/support) + тепловая матрица ошибок + пометка «baseline:
  правило-классификатор, N обращений в holdout».

### 6.5. Модуль 2 — Ассистент оператора
- **Список назначенных:** компактная таблица/карточки обращений текущего оператора
  (заглушка: фиксированный оператор либо «не назначено в регионе»). Клик → рабочий экран.
- **Рабочий экран** (`/operator/:id`) — 3 колонки, desktop-first (≥ ~1280px; ниже — стек):
  - **Слева — Текущее обращение:** полный текст, мета (регион, адрес, дата, канал, тип),
    история обращений с этого адреса/заявителя (детект повторных).
  - **Центр — Похожие кейсы:** список K похожих (pg_trgm) — превью, тема, служба-исполнитель,
    срок закрытия, резолюция, score; фильтр «только решённые»; раскрытие полной карточки.
  - **Справа — Ответ и флаги:** бейджи «Дубликат?» / «Повторное?» со ссылками;
    типовое решение (по доминирующей резолюции среди похожих); черновик ответа —
    редактируемая textarea, префилл из шаблона по теме/службе с подстановкой полей
    обращения, «Вставить шаблон ▾», копировать.
  - **Нижняя панель действий:** Маршрутизировать в службу ▾ · Сохранить черновик ·
    Отметить дубликатом (всё пишет в `mutations`).

### 6.6. Сквозное
- **FilterBar** (глобальный, в шапке): регион (7 активных + остальные disabled),
  период (пресеты + кастом), тема. Состояние в URL. Ключи TanStack Query включают фильтры.
- **Переключатель роли:** Руководитель / Оператор — меняет стартовый маршрут и видимость
  пунктов меню. Хранится в localStorage. Не безопасность, только UX.
- **i18n:** тумблер KK / RU, все строки UI в `locales/{kk,ru}.json`; значения данных
  (темы, статусы) — двуязычные подписи из `/meta`. По умолчанию RU, выбор запоминается.
- **Тема:** светлая/тёмная, уважает системную, есть тумблер.
- **Графики:** тонкие обёртки над Recharts с общими токенами (цвет темы из seed `themes`,
  единые оси/сетка/тултип). Следовать скиллу `dataviz` при реализации. У каждого графика —
  skeleton при загрузке, пустое и ошибочное состояние, доступное текстовое описание
  (`aria-label` + переключатель «показать таблицей»).
- **DataTable:** общий компонент (TanStack Table) — серверная пагинация, сортировка,
  конфиг колонок, клик по строке, липкий заголовок, переключатель плотности.
- **API-клиент:** типизированная обёртка `fetch` в `lib/api.ts`, возвращает типы из
  `packages/types`; хуки TanStack Query по ресурсам; разбор конверта ошибки; базовый URL
  из env; в деве прокси Vite `/api` → `:3001`.

## 7. Обработка ошибок
- **API:** невалидный ввод → 400 + конверт; БД/таймаут → 500 + лог; не найдено → 404;
  `/nl-query` не понял → 422 `{ summary: "Не понял запрос, уточни…" }`, без сырой SQL-ошибки.
- **Web:** `ErrorBoundary` на каждый модуль; в каждой панели — состояния loading / empty /
  error; skeleton-лоадеры; тост при ошибке мутации; баннер «API недоступен».
- **Ингест:** ошибки по строкам собираются в отчёт, прогон не падает целиком;
  жёсткий отказ только при неизвестных колонках (чтобы маппинг оставался честным).

## 8. Тестирование
- **`packages/ingest`:** юнит на каждый маппер (2–3 реальные строки → ожидаемая
  нормализованная запись); тест покрытия `theme_map` (каждая историческая категория
  маппится в тему или явно в «Прочее»).
- **`apps/api`:** `fastify.inject` на каждый эндпоинт — форма ответа, фильтры, пагинация,
  ошибки валидации; тесты интентов `/nl-query`; прогон по маленькой сид-БД (или транзакция с откатом).
- **`apps/web`:** Vitest + React Testing Library на ключевых компонентах (проводка
  FilterBar, DataTable, рендер карточки результата `/classify`, обёртки графиков на фикстурах);
  1–2 Playwright smoke-сценария (открыть центр, оператор закрывает обращение) — опционально.
- **`npm run check`** = `tsc --noEmit` + eslint по всем воркспейсам. **`npm test`** = vitest по воркспейсам.

## 10. Порядок реализации (вход для плана)
1. Скелет монорепо + общие типы + тулинг (tsconfig, eslint, tailwind, shadcn init).
2. Схема БД + seeds + один регион-маппер end-to-end + скелет ингеста → в витрине реальные строки.
3. Остальные 6 мапперов + покрытие `theme_map` + матвьюхи + предрасчёт (spikes/forecasts/eval).
4. API: `/meta`, `/kpi`, `/timeseries`, `/breakdown`, `/appeals`, `/appeals/:id`.
5. Оболочка фронта: роутинг, провайдеры, FilterBar, роль, i18n, тема, DataTable, обёртки графиков.
6. Модуль 3 — Ситуационный центр (Обзор → Всплески → Прогноз → Запрос → Отчёты).
7. Модуль 1 — Смарт-приём (Очередь → Демо-классификация → Качество модели) + `/classify`, `/model-eval`.
8. Модуль 2 — Ассистент оператора (список → рабочий экран) + `/similar`, `/duplicates`, `/templates`, `/route`.
9. Полировка (скилл frontend-design), a11y, пустые/ошибочные состояния, smoke-тесты.

## 11. Открытые вопросы (не блокируют реализацию, у каждого есть дефолт)
